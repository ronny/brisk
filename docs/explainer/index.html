How brisk works

brisk rates a code change Low Medium High with up to three reasons. Rules set a floor. A decision model, TypeSafe's Jev, can only raise the tier above that floor. The example is shelf, a repo with a Go backend and a React/TypeScript frontend. Every example assessment on this page is real output from brisk (the core thread's local main, 5cf07c3) and Jev (jev-1.14.0, through Amp).

2 · What "bad" means

There are no expert labels yet. The evaluation labels each commit by what happened to it later in git history.

Is a later commit a fix?

With a 0.7 cut-off, Jev counted features as fixes and 29–45% of changes came out bad. At 0.9, the samples read by hand were real fixes.

Where the bad labels came from

A commit can have more than one source, so the parts can add up to more than the bad total. The last 14 days of each repo are left out (censored) because a fix could still land.

From labels to metrics

Test set: the newest 40% of each repo, 487 changes, 73 bad. Each square is one change. Calibration was fitted on the oldest 60% only.

Caveat: most bad labels come from fixes. 95% of bad labels come from SZZ. SZZ blames the last commit that touched the fixed lines, and that is often a big feature commit. So the labels favour big changes. This is why diff size is the strongest feature in the fitted table (weight 0.7), and why the next step is expert labels on about 200 changes.

3 · Levers

A team sets its policy in .brisk.yaml, read from the base commit. Pick a preset, then turn any lever. The six example changes are re-scored live with their real Jev answers. local presets and levers are built on the core thread's local main (5cf07c3), not pushed.
